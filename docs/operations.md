# Her Remote 操作与验收手册

这份手册适用于本机 Her Remote 通过飞书控制 Claude / Codex 的开发、部署和验收。
目标是让“代码已修改、后台已重启、飞书端已生效”这三件事分别有证据，不把其中一件误当成全部完成。

## 一、Computer Use 正确用法

### 1. 开始前确认目标

1. 先确认当前 Computer Use 连接的是目标 Mac，而不是当前开发机或其他远程窗口。
2. 在飞书中确认目标机器人名称和输入框提示。当前目标是 `Her remote · MacBook pro2`，实际窗口可能显示为 `Her remote · Lin’s MacBook Pro`。
3. 只在目标机器的飞书窗口中做真实消息、菜单和群聊验收。
4. 需要测试哪个 bot 时，必须先确认是 `Her remote · Pro`，不要误发给“林森的her”。

### 2. 标准操作节奏

- 首次使用或重置后，先调用一次 `getState()`，读取可用应用和窗口。
- 通过应用名称或 bundle id 获取应用；名称解析失败时使用 bundle id，例如 `com.electron.lark`。
- 每次点击、输入、切换窗口后，立即重新读取 `getAXState()`，根据最新的元素编号继续操作。不要复用上一次读取的编号。
- 原生应用优先用可访问性元素操作；看不到目标文本时再取截图辅助定位。
- 浏览器任务优先新开标签页；已有明确的当前页面任务时才复用原标签页。
- 观察到最终结果后停止操作，并只调用一次 `completion_summary` 总结 Computer Use 结果。

### 3. 飞书真实验收顺序

按以下顺序做，任何一步失败都不能把后续步骤判为通过：

1. 打开 `Her remote · Pro` 私聊，确认发送对象。
2. 发送最小测试消息，确认机器人有回复。
3. 做功能操作，例如发送 `/ns codex ~/work/test1115`。
4. 确认目标目录、对应的新群、首轮结果和群内续聊都出现。
5. 如果验证写权限，让会话创建一个明确的测试文件，并读取文件确认内容。
6. 菜单更新后重新打开或刷新目标私聊，确认菜单文字实际出现。

### 4. Computer Use 失败时的判断

- `ScreenCaptureKit SCStreamErrorDomain -3811/-3812`：属于当前屏幕捕捉链路故障。不能把“点击调用返回”当成 UI 操作成功，也不能把服务端 API 成功当成客户端画面验收成功。恢复后必须重新读取目标窗口并看到最终状态。
- accessibility tree 没变化：不要连续重复同一个读取调用；先做一个明确的 UI 操作，或使用截图 / 全量 accessibility tree 获取新证据。
- 目标窗口不明确：停止真实消息操作，先重新定位窗口和发送对象。
- 只读到历史消息：只能证明历史消息存在，不能证明本次操作成功。

## 二、常驻菜单更新流程

菜单修改包含“源码、飞书能力配置、应用版本、客户端缓存”四层，必须逐层验收。

### 1. 修改前检查

- 先阅读 `bridge/botmenu.py` 文件头的真实限制和 `bridge/menu_heal.py` 的自愈规则。
- 菜单总节点数上限是 10，父节点和子节点一起计数；悬浮菜单主菜单最多 5 个，单个父菜单最多 5 个子菜单。
- 修改后必须运行 `validate_tree()`；返回空列表才允许继续。
- 菜单指纹由权限、事件、回调和菜单形状共同计算。形状变更必须触发一次新的飞书版本发布。
- 常驻菜单点击事件和卡片回调都必须订阅；只写菜单而不订阅，菜单可能显示但点击无反应。

### 2. 版本号规则

飞书版本号必须是 `X.Y.Z` 的数字形式，三个组成部分不能带前导零。不要直接使用：

```text
1.%Y%m%d.%H%M%S
```

因为凌晨或整点前十分钟可能生成 `1.20261116.062900`，飞书会返回 `50516 invalid request`。统一使用 `bridge.botmenu.version_for_time()`，并保留 `tests/test_menu_version.py` 的凌晨回归用例。

### 3. 发布顺序

1. 写入菜单能力。
2. 增量订阅收消息、常驻菜单点击和卡片回调。
3. 生成合法版本号。
4. 提交应用版本。
5. 确认飞书开发者后台的版本状态为“已发布”或“已提交待审核”。
6. 只有菜单写入、订阅和版本提交都成功，才写 `menu_heal.json` 的 `done: true`。

`50516` 发生在发布阶段时，先检查版本号格式和后台版本状态，不要重复修改菜单树，也不要把服务重启当成发布成功。

### 4. 后台部署顺序

只要修改了 `remote_control` 的代码逻辑：

1. 在仓库提交改动。
2. 备份当前运行目录 `~/.carher-feishu-agent/bridge`。
3. 将仓库 `bridge/` 同步到 `~/.carher-feishu-agent/bridge/`。
4. 对关键文件做哈希比对，至少包括 `bridge/botmenu.py` 和 `bridge/menu_heal.py`。
5. 重启 `com.carher.feishu-agent`。
6. 检查 launchd 状态为 `running`，并检查日志中有成功连接飞书的记录。
7. 检查 `menu_heal.json` 的指纹、版本和 `done` 状态。

源码目录、运行目录和飞书后台版本必须分别核对；三者没有同时对齐时，不能宣称菜单更新完成。

### 5. 客户端最终验收

服务端发布成功后，仍需在 Computer Use 中打开目标 `Her remote · Pro` 私聊，刷新或重新进入菜单，实际看到：

```text
🖥 会话   ➕ 新建会话   🧠 模型   ⚡ 常用   ⏹ 停下
```

客户端画面没有读取成功时，验收状态应记录为“服务端已发布，客户端画面待确认”，不能写成全部通过。

## 三、最小验证命令

在仓库根目录执行：

```bash
python3 -m py_compile bridge/botmenu.py bridge/menu_heal.py
python3 -m unittest tests.test_menu_version -v
python3 - <<'PY'
from bridge.botmenu import validate_tree
assert validate_tree() == []
print('menu tree: PASS')
PY
git diff --check
```

完整回归必须使用项目虚拟环境。若导入 `lark_oapi` 等依赖失败，记录为环境阻塞并修复或切换到正确环境后再判定，不得把“只跑了部分用例”写成全量通过。

## 四、交付记录

每次菜单或 Computer Use 关键验收至少记录：

- 仓库提交 SHA。
- 运行目录同步结果和关键文件哈希。
- 后台服务状态、进程和日志连接证据。
- 菜单版本号、菜单指纹和飞书后台发布状态。
- Computer Use 的目标窗口、实际操作、最终可见结果。
- 失败时的错误码、错误边界和下一步。

涉及人的后续动作或尚未取得最终客户端证据时，在项目记录中用红色字体标注。
