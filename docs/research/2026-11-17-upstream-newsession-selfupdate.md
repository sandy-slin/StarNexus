# 调研：官方新版（20261117）的「一步开新会话」和「自升级」

对比对象：官方 feishu-agent `20261117-26e4d3cf-dirty-8134126e`（只解包，未运行）与 StarNexus `6b98c54`。
上游跟踪仓库：`/Users/LinSen/work/feishu-agent-upstream`（本地 Git，每个官方版本一个提交，共 5 个版本，最新 `4a84a9e`）。

## 一、开新会话：用户要做几步

| | 官方新版 | StarNexus 现在 |
|---|---|---|
| 入口 | 会话列表顶上「➕ 新会话」，或某个工具分组里「➕ 新开一个 Claude Code」 | 菜单「新建会话」或 `/ns` |
| 用户动作 | 一张卡：工具▾（默认上次用的）、项目▾（默认最近用的）、输入第一句话**回车即开** | 点工具卡 → 点项目卡 → 机器人提示“下一句就是第一句” → 再发一条消息 |
| 次数 | 默认合适时：点 1 次 + 回车 1 次 | 点 2 次 + 发 1 条消息，中间收到 3 条机器人消息 |
| 开完之后 | 自动建群，第一轮回复贴进新群 | 自动建群（`SN·` 命名），之后在群里对话 |
| 模型/强度 | 卡上不能选 | 能选，不选用缺省模型 |
| 新项目 | 不支持 | `/ns project new` |
| 电脑上 | 自动打开一个终端窗口接着这个会话 | 不弹窗口 |
| 权限 | <font color="red">Codex、Cursor 从手机开一律只读</font> | 与终端一致，全部读写执行（林森已明确要求） |

**用户维度结论**：官方“一张卡、回车即开”明显更省事，值得借鉴；但只读权限、自动弹终端窗口、卡上不能选模型这三点与我们的要求冲突，不能照搬。

**建议的 StarNexus 新会话卡**（待实现）：

- 一张卡：工具▾（Claude / Codex / opencode，默认上次用的）、项目▾（默认最近用的，末项“➕ 新建项目…”）、模型▾（默认=缺省模型，标明“缺省”）、第一句话输入框，回车即开。
- 回车后原地换成“正在开”，不再追加提示消息；开好后建 `SN·<工具>·<项目>` 群，第一轮回复进群，私聊只留一条带“进群”按钮的结果。
- 保留 `/ns <工具> <项目> [模型] [强度] [第一句]` 作为一句话命令入口。
- 权限保持全部读写执行；不弹终端窗口；Cursor 不在范围内。

## 二、自升级：对用户的影响

- 官方新版每 10 分钟查一次官方服务器，版本号不同就下载安装包，空闲时自动安装并重启服务。
- StarNexus 现在靠 `~/.carher-feishu-agent/.local-deploy` 标记跳过自动更新（日志每 10 分钟一条“跳过自动更新”），所以**目前不会被覆盖**。
- <font color="red">官方新安装包和一行命令 `curl … install.sh | bash` 都不认这个标记。只要有人在这台 Mac 上手动运行一次，就会停掉服务、改写启动配置、用官方版整个替换 StarNexus（全权限、`SN·` 群名、opencode、CEO 等功能全部消失）。请不要在 MacBook Pro2 上运行官方安装命令。</font>
- 官方安装器成功后会删掉旧版备份，所以恢复只能靠 StarNexus 的 Git 仓库重新部署。
- <font color="red">官方新版新增崩溃上报（`errreport.py`，上报到官方服务器）；我们当前运行的启动守卫里也有一段“连续崩溃时向官方服务器报版本号和应用号”的逻辑。是否保留需要林森知悉，默认建议关掉。</font>

**方案对比**：

| 方案 | 用户感受 | 风险 |
|---|---|---|
| A 继续屏蔽官方更新 | 什么都不用做，但拿不到新功能 | 手动运行官方安装包仍会覆盖 |
| B 改成从 GitHub（sandy-slin/StarNexus）更新 | 菜单里能看到“有新版本”，点一下更新；失败自动退回 | 更新时会打断正在跑的会话，需要只在空闲时更新 |

**决策**：采用 A + B。
1. 保持屏蔽官方更新；增加“运行代码与仓库不一致”检测，被覆盖时在私聊提醒，并提供一键从 Git 恢复。
2. 自升级改为从 GitHub 拉取：发现新提交 → 跑单元测试 → 备份 → 同步 → 重启 → 60 秒内确认“桥已启动”，否则自动退回；默认由主人点按钮确认，正在干活时不装。
3. 官方新功能通过上游跟踪仓库对比后，人工挑选移植，不整包合并。
