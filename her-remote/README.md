# feishu-agent-bridge

在飞书里给机器人发消息 → 在**你自己的 Mac 上**跑 Claude Code → 结果回飞书。
手机飞书同样能用（同一个会话），所以你在外面也能指挥家里的机器。

```
手机/电脑飞书  ──►  飞书服务器  ──►  你 Mac 上这个进程  ──►  claude -p（只读）
      ▲                                      │
      └──────────── 结果 ◄───────────────────┘
```

**不需要公网 IP、不需要内网穿透。** 走飞书官方的长连接：进程主动连出去，事件顺着这条
连接进来。官方对自建应用推荐这种方式。

## 为什么不做成豆包那样的侧边栏

豆包能读本地文件靠的是 `_aha_api` → `AgentInfraService.xpc` → `libagent_infra.dylib`
这条原生链路，整个飞书 webcontent 里只有豆包自己和 `record-waklet` 在用，开放平台那侧
对 `local_runtime` / `agent_infra` 的引用数是 0，且 XPC 服务带字节跳动团队签名
（`XY6NLV7YTS`）。**这不是一道能授权打开的闸门，是没留口子。**
所以手长在 Mac 上，飞书只当嘴。代价是入口从侧边栏变成聊天窗，能力不受影响。

## 安全姿态

默认 `readonly`。这是刻意和主流开源实现相反的选择 —— 调研里最贴合需求的那个项目
（lark-channel-bridge，2784★）默认把 claude 跑成 `bypassPermissions`，README 自己承认
"工作目录不是文件系统沙箱"。

闸门在**代码里**，不是提示词里：工具白名单是进程启动参数（`--allowed-tools`），
由 Claude Code 自己的权限层执行。实测验证过：

| 试图做的事 | 结果 |
|---|---|
| 用 Write 改文件 | 被拒，文件内容未变，拒绝记录回传 |
| `rm -f` 删文件 | 被拒，文件还在 |
| 读 git 状态、搜代码 | 正常放行（审批钩子对只读白名单内的命令快捷放行，不弹卡片）|

另外任何模式下都硬拒：`rm` / `sudo` / `git push` / `git reset` / `curl` / `wget`，
以及读 `.env` / `*.pem` / `*.key` / `id_rsa*` / `.aws/` / `.ssh/`
（凭据读不到，就不会被回传进飞书 —— 飞书是外部系统，发出去等于发布了）。

**只读白名单里刻意排除的**：裸 `git`（前缀匹配会放进 `git push`）、`find`（`-exec`
等于任意执行）、`python`/`node`/`sh`（直接是任意代码执行）。

放开权限只能改 `config.toml` 的 `mode`，**聊天里说什么都不提权。**

## 装

```bash
cd tools/feishu-agent-bridge
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
cp config.example.toml config.toml      # 然后填 app_id / app_secret
```

### 飞书后台要做的（自建应用）

1. 添加应用能力：**机器人**
2. 权限管理，开这几个：
   - `im:message.p2p_msg:readonly` —— 收单聊
   - `im:message.group_at_msg:readonly` —— 收群里 @（不用群聊可省）
   - `im:message:send_as_bot` —— 回消息
3. 事件配置：订阅方式选「**使用长连接接收事件**」，添加 `im.message.receive_v1`
4. **先把本进程跑起来、长连接在线**，才能保存长连接这个订阅方式（官方明确警告）
5. **创建版本并发布**，等管理员审核 —— 不发布前面全都不生效

### 拿自己的 open_id

`owner_open_ids` 先留空启动，给机器人发一条消息，看日志里打印的 open_id，填进配置重启。
留空时**不执行任何活**（fail-closed，故意的）。

注意 open_id 是 per-app 的，换 app 要重新取。

## 跑

```bash
./.venv/bin/python -m bridge.app
```

聊天里能用 `/status`（看模式和会话）、`/new`（开新会话）、`/help`。

## 运维上必须知道的三件事

**只能跑一个进程。** 飞书长连接是集群模式、不广播 —— 同一应用多个客户端在线时
「只有其中随机一个会收到消息」。调试进程和正式进程同时开着，消息会随机漂走。
代码里用文件锁硬挡，启动第二个会直接拒绝。

**必须有外部重启。** lark-oapi 的 issue #169（至今未修）：重连路径里一个 `requests.post`
没设超时且全程持锁，半开连接下会永久阻塞 —— **进程还活着、不报错、日志直接断掉**。
报告者实测静默失联 3 天 13 小时。`auto_reconnect` 覆盖不了这种。
本进程自带看门狗：静默超 15 分钟就以退出码 75 自杀，**但拉起来要靠外面的 launchd**。

**飞书超长会静默吞消息。** 纯文本上限 150KB、卡片 30KB，超了不报错直接丢。真实案例：
agent 干完活花了钱，卡片没更新，用户盯着「正在思考」等到永远。本实现按字符留足余量、
超长拆最多 4 条并**明说有多少没发出**（不假装发完），发送失败会记 error 日志。

## 已知边界

- **只验了 claude**。`cursor-agent` 这条腿没接，调研里也没找到任何人从飞书驱动它的
  先例，属于未验证。
- **按钮审批已做，并且实测过完整闭环**。靠 `PreToolUse` 钩子返回 `defer`：进程以
  `stop_reason="tool_deferred"` 退出（不占资源、不会超时），审批卡片发到飞书，
  点「同意」后 `--resume` 同一会话接着做那一步。实测三段：停下时目标文件没动 →
  **换个会话批准同一操作不放行** → 自己批准才真执行。
  🔴 `CARHER_APPROVAL_DIR` 绝不能写进 `settings.json` —— 实测它会覆盖进程环境变量，
  后果是所有会话共用批准目录，A 批准的操作让 B 直接放行（有回归测试盯着）。
- **没做流式输出**。第一版攒完再发，只有超时进度提示。
- 长任务只有两次进度提示（90s、420s），计时器独立于模型 —— 模型完全不响应时才最
  需要提示。
